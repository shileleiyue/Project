## 核心业务
- [x] 已核验：设备列表支持关键词、类型、状态筛选和分页 — 结论：满足（`device.py` 与 `device_repo.py` 实现三类筛选、页码及每页数量限制）
- [x] 已核验：借用记录和维修工单支持分页 — 结论：满足（借用与维修列表仓储均返回 list、total、page、page_size、total_pages）
- [x] 已核验：不可借设备与重复/并发申请受到可靠限制 — 结论：部分满足（顺序请求检查设备状态；缺少行锁、条件更新或数据库唯一约束，不能保证并发时最多一单）
- [x] 已核验：正常归还流程可完成并正确恢复设备状态 — 结论：满足（用户归还进入 pending_return，管理员确认后借用为 returned、设备为 available）
- [x] 已核验：损坏归还必须填写说明、上传照片并自动生成关联维修工单 — 结论：不满足（JSON 路由不要求说明和图片，multipart 与 JSON 契约冲突，损坏分支仅改状态而不建工单）
- [x] 已核验：普通用户只能查看自己的借用和报修记录 — 结论：部分满足（`/borrows/my`、`/repairs/my` 按用户过滤，但任意登录用户可读取任意维修详情）
- [x] 已核验：维修人员只能查看、更新分配给自己的工单 — 结论：部分满足（assigned 列表和状态更新按 assigned_to 限制，但详情读取及图片上传未限制）
- [x] 已核验：维修人员提交完成后设备不会直接恢复可借 — 结论：满足（维修人员提交 repaired 后设备为 repaired，仍待管理员确认）
- [x] 已核验：管理员确认后设备才恢复可借或标记报废 — 结论：满足（仅 admin 可确认；repaired→available、unfixable+scrap→scrapped）
- [x] 已核验：审核记录和设备状态变更记录可按角色要求查看 — 结论：部分满足（借用/维修业务写入审核日志且管理员可查；设备新增、编辑、下架、删除未写状态日志，维修及设备日志字段也不完整）

## 安全与接口
- [x] 已核验：公开注册不能自行获得管理员或维修人员权限 — 结论：不满足（注册 schema 接收 role，服务接受 admin/repairer；定向实测可公开注册 admin）
- [x] 已核验：维修详情、图片上传和状态更新不存在跨用户越权 — 结论：不满足（详情与图片接口仅要求登录；定向实测跨用户详情和越权上传均返回 200；状态更新仅校验 assigned_to）
- [x] 已核验：用户禁用、删除或角色变化后旧 Token 权限得到合理处理 — 结论：不满足（鉴权只信任 JWT 内 user_id/role，不回查用户存在、启用状态或当前角色；严重度按 major）
- [x] 已核验：上传文件格式、真实内容、大小和数量限制有效 — 结论：部分满足（后端限制扩展名及单文件 5MB，但不校验 MIME/魔数、不限制文件数量，保存后数据库失败会遗留孤儿文件）
- [x] 已核验：上传路径配置生效且数据库路径可被前端跨平台访问 — 结论：部分满足（静态 `/uploads` 已挂载，但 `UPLOAD_DIR` 未使用，保存依赖工作目录且数据库保存 Windows 反斜杠相对路径）
- [x] 已核验：API 成功与失败响应均遵循统一 Result 结构 — 结论：不满足（业务成功使用 Result；HTTPException、422 与未捕获异常仍为 FastAPI 默认 detail 响应，根路由也非 Result）
- [x] 已核验：密码安全存储，密钥和数据库凭据未硬编码或泄露 — 结论：部分满足（密码使用 bcrypt；配置源码仍含固定 JWT 密钥和默认数据库口令，部署必须覆盖）
- [x] 已核验：数据库操作使用 ORM/参数化查询且关键业务异常得到处理 — 结论：部分满足（查询使用 SQLAlchemy；并发借用、状态机跳跃、分配人员角色、borrow/device 关联与非法枚举边界处理不足）
